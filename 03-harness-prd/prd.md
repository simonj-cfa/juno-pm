## Problem & user

RocketShip PMs need this handled: June populates a customer insights dashboard, updated daily from real-world customer feedback. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Juno should pull customer insights from the following data sources (beginning from January 1, 2026):
-Recordings, transcripts, and notes from customer interviews.
-Jira support tickets and attached context.
-Data from calendarized marketing and product surveys.
-NPS and feedback surveys from live products.
-Juno should also have access to the simulation wireframes, for contextual understanding of individual projects.

**How fresh must it be**

-Data sources should be queried daily.
-Data loss should be specified - if a source is unreachable, the human in the loop should be queried.

## 02 Tools · System Capabilities

**The verb list**

-Juno reads, synthesizes, and summarizes data, which is populated on the customer dashboard.
-On a daily basis, Juno will read the documented source files to find updated customer insights.
-Juno cannot modify or edit the raw customer data itself. The only written output Juno provides are summary insights via the dashboard. All insights need to be tied to real evidence, prioritizing direct customer feedback/quotes.

**Deliberate omissions**

-Juno does not have the power to edit or mutate the data. Our customer data is sensitive and should not be edited - Juno can read it and summarize/synthesize, but cannot mutate it directly.
-Juno is not making product decisions, or deciding what to build and why.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

Two passes. A first pass for preliminary insights, and then a second to secure supporting evidence or establish repeated claims/themes, and reviewing for duplication. The goal is to establish clear evidence for each claim, and to cite multiple sources of evidence wherever possible.

**Latency and cost target**

The customer dashboard receives a daily update so quick results are not necessary.

## 04 Memory · Data Requirements

**What persists, at what scope**

-Data uploaded to the dashboard is persistent and updated daily.
-Individual instances of customer feedback should not be re-ingested daily or duplicated / double-counted.

**Expiry and write rules**

The insights do not expire, but a given piece of data should not be counted twice.
The human in the loop can choose to disregard individual sources of customer feedback.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | blocked |
| send | blocked |

**Justification**

-Read: Auto - can read data.
-Draft: Auto - can draft sourced-insights, this is what goes to the dashboard.
-Write: Blocked - cannot mutate customer data sources.
-Send: Blocked - cannot share insights other than to human in the loop or to dashboard.
-Send: Blocked
-Juno may only post exclusively to the insights dashboard. It cannot modify the source data in any way.
-Juno may summarize high-level themes or feedback surfaced across multiple sources of data, but cannot change the data itself.
-Juno cannot post PII. Customer information can only be posted according to specified user format (ie, chartholder/learner type, region, etc).

## 06 Verification · AI Testing & Measurement

**The check before output ships**

Any insight posted to the dashboard should be accompanied by at least one real signal in the source documentation. All evidence must be cited. Juno should check its work against source data before posting to the customer insights dashboard.

**Failure behaviour**

If a search for evidence fails, the human in the loop should be queried.
